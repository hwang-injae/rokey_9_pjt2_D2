## 2. 코드 작성

### 2-1. 🆕 규칙 1 — 관련 기능은 클래스로 묶는다

- 한 노드(모듈) 안의 관련 기능은 클래스 하나로 묶어 관리한다. 예: 그리퍼 노드 = `GripperNode` 안에 열기·닫기·폭 읽기.
- **노드 하나 = 노드 클래스 하나 = 파일 하나.** 노드가 쓰는 계산 클래스(ROS 없이 도는 것)는 같은 패키지의 다른 파일로 나눠도 된다 — 다른 사람이 맡거나 ROS 없이 시험할 때만(규칙 2 과도한 구조화 금지). 예: 그리퍼 노드 = `gripper_node.py` 하나 (10/5 S-14).

### 2-2. 🆕 규칙 2 — 불필요한 일회성 참조, 과도한 구조화 금지

- 한 번만 쓰는 값·함수를 따로 빼서 여기저기서 참조하게 만들지 않는다.
- '나중에 쓸지도 모르는' 추상 클래스·계층·설정 단계를 미리 만들지 않는다. 지금 필요한 만큼만 짠다.
- 두 번 이상 쓰이는 값(작업대 높이·좌표·그리퍼 값 등)은 **설정 파일 한 곳**에 둔다.

### 2-3. 경로는 하드코딩하지 않는다

- `/home/이름/...` 같은 개인 경로를 코드·launch·설정에 쓰지 않는다. 팀원마다 경로가 다르다.
- 패키지 기준 경로(`get_package_share_directory`)나 파일 기준 상대 경로(`Path(__file__).parent`)를 쓴다.
- 실행 명령은 README에 그대로 복사해 쓸 수 있게 적는다.

### 2-4. 단위·이름

- 내부 단위는 m(라디안), 파일(설계·설정)은 mm로 쓴다.
- 블록 번호는 레시피의 block_id(예: `LV1_B001`)로 통일한다.

### 2-5. 로봇을 움직이는 코드는 정지 처리를 반드시 넣는다

- Ctrl+C·막힘·실패 때 **먼저 로봇을 세우는**(서기 궤적) 처리를 넣는다. 예시는 [`research/ref_1003/R-01_정지/safe_stop.py`](research/ref_1003/R-01_정지/safe_stop.py)와 박진용이 10/4 실기에서 확인한 Ctrl+C 정지 코드(PR로 올라옴)다.
- 프로그램이 끝나도 이미 보낸 궤적은 계속 움직일 수 있다. 그래서 이 처리가 필요하다(10/3 가상 시험).

### 2-6. 🆕 규칙 10 — 주석으로 동작을 설명한다 (10/6 PL)

다른 사람(다른 파트·통합하는 사람)이 코드를 열었을 때 주석만 읽어도 무엇을 하는지 알 수 있게 한다. 에이전트가 만든 코드도 같다.

- **클래스:** 맨 위 docstring에 이 클래스가 맡는 일을 적는다. 노드면 받는 것·내보내는 것(토픽·서비스·액션 이름)도 적는다.
- **함수·메서드:** docstring에 ① 무엇을 하는지 한 줄 ② 입력·출력(단위 포함) ③ 바깥에 주는 영향(로봇·그리퍼를 움직임, 메시지를 보냄, 파일을 씀)이 있으면 그것 ④ 실패하면 어떻게 되는지(반환값·예외)를 적는다. 짧고 뻔한 함수는 ①만으로 충분하다.
- **코드 안 주석:** '무엇'보다 **'왜'**를 적는다 — 숫자(기다리는 시간·여유값), 순서가 중요한 곳, 정지·안전 처리, 우회 코드. 코드를 그대로 읽어 주는 주석(`i += 1  # i를 1 늘림`)은 쓰지 않는다.
- 주석은 **한국어**, 이름(변수·함수·클래스)은 영어로 쓴다.
- 코드를 고치면 주석도 같이 고친다. 틀린 주석은 없는 것보다 나쁘다.

예시(형식만 보는 것 — 이름·값은 실제 코드와 다를 수 있다):

```python
class GripperNode(Node):
    """RG2 그리퍼를 다루는 유일한 노드.

    받는 것: 그리퍼 서비스(폭·힘)
    돌려주는 것: 다 움직인 뒤 잡힘 여부와 실제 폭
    """

    def close_to(self, width_mm: float, force_n: float) -> bool:
        """그리퍼를 width_mm까지 닫고, 블록을 잡았으면 True를 돌려준다.

        다 움직인 뒤에 답한다. 통신이 끊기면 예외를 밖으로 던지지 않고 False.
        """
        ...
        time.sleep(0.2)  # 왜: 닫힌 직후에는 폭 값이 흔들려서 잠깐 기다린 뒤 읽는다
```

## 3. GitHub

### 3-1. 브랜치

```
{이름}/{날짜 YYYYMMDD}-{기능}-{간단설명}
예: 황인재/20261005-hmi-web-buttons
    한세교/20261006-motion-scene-manager
```

- `{이름}`은 **한글 이름**이다(10/6 PL — GitHub ID가 아니다). 설명은 영문 kebab-case. 브랜치는 `/today`가 만들어 준다.

- 설명은 영문 kebab-case로 쓴다(공백·한글로 생기는 문제 방지).
- `main`은 보호한다(10/4 적용). PR로만 반영하고 직접 push는 막는다. **관리자(황인재)만 예외**다. **10/6 PL: 황인재는 문서뿐 아니라 코드도 PR 없이 main에 바로 push한다** — 황인재 PR은 한세교가 승인해야 하는데 한세교 일이 많아서다. 그 밖의 사람은 PR로만 올린다.
  - **대신 push 전에 스스로 검사한다(10/6 PL):** `python3 .github/scripts/pr_check.py --repo . --base origin/main`(PR 검사와 같은 검사 — main 반영·충돌·문법·키·문서 이름·정지 설정)를 통과해야 push한다. 코드면 `/pr-review` 기준 ①~⑧로 스스로 한 번 본다. 끝낸 작업은 커밋 메시지에 `완료: W번호`를 적는다(문서담당이 커밋 메시지에서 읽는다). `/wrap`이 이 순서로 한다.
- 주의: GitHub 무료 플랜의 **비공개** 저장소에서는 브랜치 보호·CODEOWNERS 승인이 강제되지 않는다. 그런 저장소라면 공개 저장소로 하거나(키는 어차피 올리지 않음), '승인 전 merge 금지'를 사람이 지킨다.

### 3-2. 🆕 규칙 7 — PR 승인은 황인재·한세교, 검사·승인은 자동

- `main`에 들어가는 모든 PR은 **황인재(@hwang-injae) 또는 한세교(@hansaekyo)의 승인**이 있어야 merge된다(`.github/CODEOWNERS` + 브랜치 보호 'Require review from Code Owners').
- **PR을 올리면 'PR 검사'가 자동으로 돈다**(`.github/workflows/pr_check.yml`):
  1. **main 반영** — 최신 main을 내 브랜치에 merge했는가. 안 했으면 실패한다 → `git fetch origin && git merge origin/main`(충돌은 내 PC에서 푼다) 뒤 다시 push.
  2. **충돌** — main과 합칠 때 충돌이 없는가.
  3. **문법** — 바뀐 파이썬(실행하지 않고 컴파일만)·YAML·JSON·XML(launch·urdf·xacro).
  4. **비밀값** — OpenAI 키 모양 문자열·`.env`·키 파일이 없는가(규칙 4).
  5. **변경 파일** — PR 본문 '변경 파일' 칸이 채워져 있는가(규칙 8). 개별 커밋의 `변경 파일:` 줄은 경고.
  6. **문서 이름** — `docs/` 아래 새 문서가 `이름_v<버전>_<MMDDHH>.md`인가(규칙 9).
  7. 🆕 **정지 설정** — 로봇을 움직이는 `.py`를 바꾼 패키지에 Ctrl+C 정지 설정(`SignalHandlerOptions.NO`·`init_ros`)과 서기 정지 호출(`SafeStop`·`move_stop`)이 있는가(2-5). 단어가 있는지만 본다.
- 🆕 **위 검사를 통과하면 Claude가 PR을 검토한다**(10/6 PL, 팀원 PR만). 기준은 `/pr-review`와 같은 ①~⑧(정지 처리·장면 관리 노드·`/d2/` 이름·robot.yaml·클래스·남의 파트·키·docstring)이고, 결과표를 PR에 남긴다.
  - ①~⑧에 **'막음'이 없으면 자동 승인**, 있으면 **'수정 요청'**(Request changes) + 고칠 곳(파일:줄). 고쳐서 다시 push 하면 검사·검토가 다시 돈다.
  - Claude 검토가 돌지 못하면 승인하지 않고 코멘트만 남긴다 → 승인자가 `/pr-review 번호`로 본다.
  - Claude 판정은 틀릴 수 있다. 승인자는 결과표를 보고 직접 승인·거절할 수 있다. 자동 '수정 요청'이 틀렸으면 그 리뷰를 **Dismiss(취소)한 뒤 승인**한다(승인만 누르면 수정 요청이 남아 merge가 막힌다). '통과'가 실제로 로봇이 서는 것을 보장하지는 않는다(정지는 실기 시험으로 확인).
- 자동 판정 계정은 **황인재**다(저장소 비밀값 `D2_APPROVER_TOKEN`에 황인재 토큰, 10/4 PL 결정). 그래서 **황인재가 올린 PR은 결과표만 코멘트로 남고 한세교가 직접 승인**한다(GitHub은 본인 승인을 막는다). 10/6부터 황인재는 PR 없이 바로 push하므로 이 경우는 거의 없다. 황인재·한세교는 언제든 직접 승인·거절할 수 있다.
- merge 방식은 `Squash and merge`이고, squash 커밋 메시지는 **'PR 제목 + 본문'**(Settings → General)으로 둔다. 그래서 main 기록에 '변경 파일' 목록이 남는다. merge된 브랜치는 GitHub이 자동으로 지운다(10/6) — 이어서 할 일은 날짜를 바꾼 새 브랜치를 `main`에서 판다.

### 3-2-1. 🆕 작업 완료는 PR로 알린다

- 일정표(드라이브) Time Line의 작업에는 번호 `[W001]`~가 있다.
- 작업을 끝내면 PR 본문 '완료한 일정표 작업' 칸에 `완료: W041, W047`처럼 적는다. 아직 하는 중이면 `진행: W041`.
- PR이 merge되면 **PL의 문서담당 에이전트가 확인해 일정표 상태를 '완료'(또는 '진행 중')로 바꾸고** 드라이브의 같은 파일을 갱신한다.

### 3-3. merge 전 확인

```bash
git fetch origin
git merge origin/main   # 충돌은 PR 올리기 전에 내 PC에서 푼다
git push
```

- 작업 중에도 오전·오후 한 번씩 `git fetch`로 뒤처졌는지 본다.
- 공통 파일(README, 설정 파일, 인터페이스·메시지, launch, `package.xml`)은 혼자 구조를 바꾸지 않고 먼저 알린다.
- 진행 중인 일은 Draft PR로 미리 열어 '누가 이 파일을 만지는지' 보이게 한다.
- `build/`, `install/`, `log/`, `__pycache__/`는 커밋하지 않는다. 공유 브랜치에서 rebase·force-push를 하지 않는다.

### 3-4. 🆕 규칙 8 — 바뀐 파일을 적어서 토큰을 아낀다

에이전트가 pull 할 때마다 저장소 전체나 전체 diff를 읽으면 토큰이 많이 든다. 그래서 **바뀐 파일을 커밋 메시지와 PR에 적고, 에이전트는 그 파일만 읽는다.**

**커밋 메시지**

```
feat: MoveIt 실행기에 서기 정지 추가

- 실행 중 '서라'를 받으면 현재 자리 0.3초 궤적을 보냄
변경 파일: src/jenga_motion/jenga_motion/executor.py, src/d2_bringup/config/robot.yaml
영향: 로봇 동작(실행기), 비전 없음
```

| 접두어 | 쓸 때 |
|---|---|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 같고 구조만 개선 |
| `chore` | 설정·패키지 구성 같은 잔일 |
| `docs` | 문서 |

- 제목 한 줄 + (단순하지 않으면) 이유 2~3줄 + **`변경 파일:`** + **`영향:`**(어느 파트·묶음에 영향이 있는지)을 쓴다.
- '수정', 'update' 같은 뜻 없는 메시지는 쓰지 않는다. 커밋 하나에 작업 하나를 담는다.

**PR**: 양식의 '변경 파일' 칸에 파일 목록을 적는다.

**에이전트 읽기 규칙**: 저장소 맨 위 `AGENTS.md`(Claude는 `CLAUDE.md`, Gemini는 `GEMINI.md`로 같은 내용)에 적는다.

1. pull 뒤 이번에 들어온 커밋의 제목·본문(`변경 파일:`·`영향:`)과 바뀐 파일 목록만 본다.
   ```bash
   git log --format='%h %s%n%b' ORIG_HEAD..HEAD
   git diff --stat ORIG_HEAD..HEAD
   ```
2. PR을 볼 때는 `gh pr view <번호> --json title,body`로 본문의 '변경 파일'만 본다.
3. 그 목록에 **내 담당 파일**이 있을 때만 그 파일을 연다.
4. 전체 diff·이전 버전 비교·저장소 전체 읽기는 사람이 요청할 때만 한다.
5. 맨 위 `CHANGES.md`는 맨 위 요약(최근 며칠)만 읽는다. 하루를 마칠 때 파트마다 한 줄씩 적는다.

### 3-5. 이슈

- 이슈는 할 일 관리가 아니라 **트러블슈팅 기록**에만 쓴다(할 일은 노션·일정표).
- 원인 찾는 데 오래 걸렸거나 팀이 같이 알아야 할 에러일 때 연다. 양식은 `.github/ISSUE_TEMPLATE/bug_report.md`다.
- 해결하면 댓글에 해결 방법을 남기고 닫는다. 관련 PR 본문에 `Closes #번호`를 쓴다.

## 4. 보안

### 4-1. 🆕 규칙 4 — OpenAI API 키는 절대 GitHub에 올리지 않는다

- 키는 **PC마다 `.env`** 파일에만 두고, 코드는 환경 변수로 읽는다.
- 키를 코드·설정·노트북 셀·커밋 메시지·이슈·노션·채팅에 붙이지 않는다.
- 커밋 전에 `git status`와 `git diff --stat`으로 `.env`나 키가 든 파일이 없는지 본다.
- 실수로 올렸으면 **바로 PL에게 알리고 그 키를 폐기**한 뒤(PL이 강사에게 폐기·재발급 요청) 새 키를 받는다. 커밋을 지워도 기록에 남으므로 폐기가 먼저다.
- 컨테이너 안에서 키가 필요하면 `docker run --env-file .env ...`로 넘긴다. 키를 Dockerfile·이미지에 넣지 않는다.

### 4-2. GitHub에 올리지 않는 것

GitHub 토큰(PAT), 비밀번호, API 키, 인증서·개인 키, 개인 계정 정보. `.gitignore`에 `.env`, `.env.*`, `*.pem`, `*.key`, `credentials.json`, `secrets.yaml`을 기본으로 넣는다(저장소의 `.gitignore`).

## 5. 컨테이너 (Docker)

### 5-1. 🆕 규칙 5 — 컨테이너는 지우기 전에 꼭 확인

- 지우기 전에 `docker ps -a`로 이름·이미지·만든 사람을 확인한다. **내가 만든 것이 아니면 만든 사람에게 먼저 묻는다.**
- `docker rm -f $(docker ps -aq)`, `docker system prune` 처럼 한꺼번에 지우는 명령은 쓰지 않는다.
- 컨테이너 이름에 파트·이름을 붙인다. 예: `hmi-<이름>`, `db-hmi`. 컨테이너는 그 안에 넣는 노드의 담당이 만든다(10/5 S-17). **10/6 주제 개편(E-19)으로 웹캠을 쓰지 않아 `vision` 컨테이너는 없다 — 컨테이너는 `hmi` · `db-hmi` 2개(둘 다 황인재).**

### 5-2. 🆕 규칙 6 — 원본 자료는 컨테이너에 넣지 않는다

- 녹화 데이터(rosbag)·대용량 CAD·DB 데이터 같은 원본은 **로컬 PC 폴더에 두고 컨테이너에 연결(마운트)** 해서 쓴다.
- 설정 파일·레시피는 저장소에서 버전 관리한다. 컨테이너에는 복사하지 않고 **로컬 저장소 폴더를 연결**해서 읽는다.
  ```bash
  docker run -v ~/jenga_data:/data:ro ...   # 읽기만 할 원본은 :ro
  ```
- Dockerfile에서 원본 자료를 이미지 안으로 복사(`COPY`)하지 않는다. 컨테이너를 지워도 원본은 남아야 한다.
- DB 데이터도 이름 있는 볼륨이나 로컬 폴더에 둔다.
