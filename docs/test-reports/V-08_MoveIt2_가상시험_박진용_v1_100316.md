# V-08 MoveIt2 경로 · 회피 가상 시험 1~3차 (10/3, 박진용)

> 10/3 사전 검증 작업 3의 결과 보고서(노션)를 저장소로 옮겼다. 내용은 그대로이고 제목과 이 안내만 더했다. 영상(`*.webm`)과 코드(`*.py` · launch · urdf · srdf)는 저장소에 넣지 않았다 — 팀 노션 결과 페이지에 있다. 요약은 [결과표](../04_결과_결과표_v2_100712.md) §3, 정지 문제는 [TS-01](../troubleshooting/TS-01_정지가_안_들음_R-01_v1_100519.md)에 있다.
>
> 검증 수준: **가상**(두산 에뮬레이터). 10/3 저녁 실기(V-07)와 10/4 실기 재검증은 이 보고서에 없다. TCP 228 mm와 작업대 위 로봇 위치는 가정값이다.

    ## 2. 사용한 알고리즘
    
    | 단계 | 알고리즘 / 모듈 | 역할 |
    | --- | --- | --- |
    | 경로 계획 | OMPL RRTConnect (기본 플래너) | 관절 공간에 무작위로 점을 뿌리고, 시작과 목표 양쪽에서 트리를 뻗어 이어지면 경로 완성. 이후 경로 단축·스무딩 |
    | 충돌 검사 | FCL | 로봇 링크끼리, 로봇과 장애물 사이 충돌 판정 |
    | 계획 전 검사 | CheckStartStateCollision, CheckStartStateBounds, ValidateWorkspaceBounds | 시작 자세가 충돌하거나 관절 한계를 벗어나면 계획 거부 |
    | 계획 후 처리 | TOTG (AddTimeOptimalParameterization), ValidateSolution | 경로에 속도·가속도·시간 부여, 최종 경로 재충돌 검사 |
    | 목표 지정 | 관절 목표 (JointConstraint, 허용 오차 ±0.001 rad) | 관절값을 직접 지정 (IK 미사용) |
    | 순기구학 | compute_fk 서비스 | 미리보기 로봇과 플랜지 경로 선 계산 |
    | 실행 | ExecuteTrajectory → ros2_control → dsr_controller2 → 에뮬레이터 | 계획된 궤적 실행 |

    ## 5. 테스트 방법
    
    각 이동마다 아래를 수행. 1~3은 스크립트로 계획만 했고 로봇은 움직이지 않음.
    
    1. **시작·목표 자세 유효성**: check_state_validity로 시작·목표 자세가 장애물과 부딪히지 않는지 확인
    2. **장애물이 실제로 길을 막는지**: 시작→목표를 관절 공간 직선으로 41개 점으로 나누고 각 점의 충돌을 검사. 충돌이 있으면 "회피하지 않으면 부딪히는 배치"로 판단
    3. **계획 반복**: 같은 조건으로 OMPL 계획을 5번씩 하고 성공 여부, 계획 시간, 경로 점 수를 기록
    4. **눈으로 확인**: RViz 미리보기로 회피 경로를 확인하고, 가상 모드에서 실행 (demo_move.py)

    ## 7. 발견한 것
    
    | 항목 | 내용 |
    | --- | --- |
    | 경로가 매번 다름 | RRTConnect는 무작위 샘플링이고 처음 찾은 경로를 반환함. 같은 A→C도 이동 시간이 5.8~14.5 s로 차이남 |
    | 가끔 계획 실패 | 이전 로그에서 ValidateSolution → INVALID_MOTION_PLAN 확인 (계획 후 최종 충돌 검사 탈락). 재실행하면 성공. 시나리오 3의 1회 실패는 로그로 원인을 확인하지 않음 |
    | 시작 자세 충돌 검사 동작 | 사람 팔을 처음에 높게(0.42~0.60 m) 배치했을 때 A 자세의 팔뚝(link_4)과 겹쳐 CheckStartStateCollision이 계획을 거부함 → 배치를 조정함 |
    | 링크 높이 | A·C 자세에서 플랜지 0.35 m, 손목(link_4/5) 0.47 m. 장애물은 손목 높이까지 고려해서 배치해야 함 |
    
    ## 8. 한계

    | 경로 단축 | 지름길 다듬기 (shortcut) | ① 앞에서부터 가장 멀리 직선으로 갈 수 있는 점으로 건너뛰기 ② 무작위 두 점 직선 연결 시도. 1° 간격으로 충돌·자세 검사, 난수 시드 고정 |

    | 시간 매기기 | 자체 구현 (앞뒤 두 번 훑기) | 관절 속도·가속도 한계(× 0.1) + 곡률에 의한 속도 한계, 경유점에서 멈추지 않음 |

    | 안전 여유 | 장애물 부풀리기 | 실제 장애물 + 4 cm 부풀린 반투명 안전 영역을 같이 넣음 → 로봇은 그 바깥으로만 지나감 |

    ## 6. 테스트 방법
    
    **A. 플래너 비교 (프리셋 1, 계획만, 방법마다 구간당 5회)**
    
    - 모든 계획에 공구 아래 방향 제약
    - 측정: 성공률, 전체 이동 시간(구간 합), 점수, 손목 회전, 계획(+다듬기) 시간, 반복 간 표준편차
    
    **B. 배치 검증 (계획만)**
    
    - 경유점 IK 가능 여부, 시작·목표 자세 충돌 여부
    - 경유점 사이를 관절 직선으로 31점 나눠 충돌 검사 → 장애물이 실제로 길을 막는지 확인
    - 구간마다 BiTRRT 3회 계획 성공 여부

    ## 9. 발견한 것
    
    | 항목 | 내용 |
    | --- | --- |
    | 반응 지연이 가장 중요 | 감시 루프가 1~2 s 막히면 그 사이 손이 닿음. 실시간 경로에서는 다듬기보다 반응 속도 우선 |
    | 예측이 갈아타기를 가능하게 함 | 손의 0.5 s 뒤 위치를 넣기 전에는 갈아탐 0회 (늦게 알아채서 멈춤만), 넣은 뒤 1.1~1.5 s 전에 알아채고 갈아탐 |
    | 막힌 원인 구분 필요 | 손 때문인지 타워 같은 고정 물체 때문인지 나눠야 함. 안 나누면 영원히 기다림 |
    | 기다리는 위치가 중요 | 목표(타워) 옆에서 기다리면 사람 손이 그쪽으로 와서 닿음 → 대기 자세로 물러나야 함 |
    | 사람 의도 활용 | 사람이 칸을 예약하고 다가오는 중이면 미리 물러남 (손 위치만 보는 것보다 빠름) |
    | 놓은 뒤 올라오기 | 꼭 수직일 필요 없음. 막히면 대기 자세로 가는 게 맞음 |
    | 컨트롤러 조건 | 궤적 점 시간이 0보다 크고 엄격하게 증가해야 받음 (같은 시간이 있으면 통째로 거부) |
    | 콜백 안 서비스 호출 금지 | 구독 콜백에서 장면 갱신 서비스를 부르면 "Executor is already spinning" → 콜백은 기록만, 주 루프에서 반영 |
    | 에뮬레이터 잔여 | 이전 브링업 프로세스·에뮬레이터가 남아 있으면 컨트롤러 설정 실패 → 브링업 전 docker ps 확인 |
    
    ## 10. 한계
    
    - **가상 모드 + 가짜 손**만 테스트. 실제 손은 더 빠르고 예측하기 어려움
    - **손 인식 지연 없음**: 카메라 인식 지연(대략 0.1~0.2 s)을 넣지 않음
    - **4 cm 여유를 완전히 지키지는 못함**: 움직이는 중 0.96 s 침범 (실제 손과는 닿지 않음)
    - **기다리는 시간이 김**: 블록당 시간의 약 20%가 멈춤 (40.9 s / 199.6 s). 갈아탐 2회 vs 멈춤 26회
    - 갈아탈 때 새 경로가 속도 0에서 시작해 잠깐 느려짐
    - 블록은 물리 시뮬레이션 없이 장면 물체로만 놓음 (미끄러짐·쓰러짐 없음)
    - TCP 228 mm, 작업대에서 로봇 위치(폭 방향 가운데)는 가정값
    - 시드 1 패턴 한 가지로 최종 1회 측정. 반복 측정 필요
    - 화면 녹화 없음 (스크립트 자동 실행)
