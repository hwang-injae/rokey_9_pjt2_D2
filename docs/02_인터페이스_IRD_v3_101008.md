## 1. 원칙

1. **판단은 한 곳에서 한다.**

   | 무엇을 | 정하는 노드 | 보고 정하는 것 |
   |---|---|---|
   | 멈출지 | **정지 노드** | 정지 입력(화면 버튼 · 키 · Ctrl+C), 로봇 알람, 시간 초과(작업 관리자 요청). 그리퍼 응답 없음 · `ERROR`는 작업 관리자가 `ERROR`로 멈춘다(정지 노드 잠금 없음 — 10/9 E-74). (카메라 연결 끊김은 나중에) |
   | 진행표(블록마다 놓였나) | **작업 판단**(task 노드 안 TaskPlanner) | 손목 블록 인식 결과 + 레시피. 블록 있음 · 없음 + 높이, 오차는 측정값만 |
   | **설계가 쌓을 만한지**(새) | **검사 묶음**(task 노드 안 DesignChecker, ROS 없는 계산) | 블록 JSON(`blocks/2.0`) → 안정성 · 받침 · 틈 · 잡기 · 막힌 칸 · 작업영역 + AI가 쓴 칸(role · part · stage · grasp) 검사(10/8 E-69 — 빠지거나 틀리면 `CHECK_FAILED`, 코드가 대신 채우지 않음). 통과하면 변환기 ①로 레시피(구조 + 조립 방법)까지 |
   | **무엇을 쌓을지**(새) | **사람**(화면 · 음성으로 설계 선택 · 출발) | AI가 만든 설계도 사람이 출발을 눌러야 로봇이 움직인다(SR-09) |
   | MoveIt2 장면 | **장면 관리** | 진행표(쌓인 블록 · 스캔한 실물 블록) + 쥔 블록 붙이기 · 떼기 |
   | DB에 무엇이 들어가나 | **HMI**(design_store) | 생성 설계는 검사를 통과한 후보 중 사람이 고른 1개를 저장(10/8 E-67 — 8.3 ⑥), 조립 결과는 작업 관리자가 넘긴 것 |

   비전은 관측 결과(있음 · 없음 · 높이 · 점군 추론)만 보낸다. 차례 판단(협동)은 없다.
2. **메시지 방식은 섞는다.** 요청-결과(집기 · 놓기, 이동, 진행 확인, 그리퍼, 장면 붙이기, 화면 명령, 정지, **설계 검사, 설계 꺼내기, 스캔 촬영 · 추론**)는 서비스 · 액션. 상태 방송(진행표 · 상태 · 스캔 결과 · 카메라 신호 · 그리퍼 상태)은 JSON 토픽. **JSON 덩어리를 주고받는 요청-결과는 `JsonQuery.srv` 하나로**(칸마다 srv를 만들지 않는다 — 팀 규칙 ② 과도한 구조화 금지).
3. **이름은 모두 `/d2/` 아래**: `/d2/hmi`, `/d2/safety`, `/d2/vision`, `/d2/task`, `/d2/motion`, `/d2/gripper`.
4. **단위.** 노드끼리 m · rad · 쿼터니언. 파일(레시피 · CSV)과 **블록 JSON은 mm**(설계 좌표계). `robot.yaml`은 키에 `_m`, 값 m(S-28).
5. **결과 형식.** `success` + `reason`(7장).
6. **JSON 규칙.** 맨 앞 `"schema": "<이름>/<앞>.<뒤>"`(예 `recipe/2.0` — 점 없는 옛 이름 `state/1` 등은 다음에 바뀔 때 옮김), 시각 `stamp`(초). 버전을 올리는 규칙은 6장 **'형식 버전 규칙'**(10/8 E-69 — 옛 "형식을 바꾸면 `/2`" 대신): **깨지는 변경 = 앞자리 +1(뒤 0), 호환 확장 = 뒷자리 +1.** 읽는 쪽은 앞자리가 같으면 받고 모르는 칸은 무시, 다르면 거절.
7. **좌표**는 `base_link`. 설계 좌표(블록 JSON · 레시피)는 조립 원점(`assembly_origin`)으로 바꾼다 — 작업 판단 한 곳에서.
8. **블록 이름**(E-52): 레시피 파일 안은 `<역할>[_<옵션>]_<부품>_<블록>`(예 `LEG_001_01`), 노드 사이 `block_id`는 `<design_id 대문자>_<블록 이름>`(예 `001_CHAIR_BENCH_LEG_001_01`). 생성 · 스캔 설계도 역할 · 옵션은 AI가 `blocks/2.0`의 `role` · `part`로 쓰고, 번호(부품 · 블록)는 변환기 ①이 매긴다 — `BLOCK_<부품>_<블록>` 이름은 없앰(→ 10/8 E-69). 블록 이름에서 설계 이름을 잘라 내지 않는다(설계는 `design_id` 칸으로).
9. **장면은 장면 관리 노드만 고친다.**
10. **출발은 두 길 중 하나** — 화면 버튼 · 키(`hmi/command start`) 또는 음성(`hmi/intent start`). **잠금 풀기는 화면 '다시 시작'(`safety/resume`) 한 번**(S-24).
11. **멈출 때는 서기 궤적을 제어기에 직접** — **토픽 `/dsr_moveit_controller/joint_trajectory`** 로 보낸다(액션 `FollowJointTrajectory`는 실기에서 서지 않았다 — 10/4 R-01, 10/6 박진용).
12. **(새) 설계는 블록 JSON으로 오가고, 로봇에는 레시피로 간다.** 생성(HMI) · 스캔(비전)은 블록 JSON을 만들고, 검사 묶음이 통과시키며 레시피로 바꾼다. 로봇 쪽 노드(작업 판단 · 집기 · 놓기 · 장면)는 레시피만 안다 — 조립 엔진은 바뀌지 않는다. **(→ 10/8 E-69:** 생성 · 스캔 모두 GPT가 `blocks/2.0`(위치 · 방향 + 역할 · 부품 · 단계 · 잡기)을 쓰고, 변환기 ①은 번호 · 중심 · R · 받침 · 닫힘 축만 계산한다. 레시피 = 구조 `recipe/2.0`(`_recipe.json`) + 조립 방법 `placements/2.0`(`_placements.csv`) — 6장)
13. **(새, E-27~E-29) PC 사이는 MQTT 다리 한 곳.** 웹 PC(화면 · 생성 · 저장소 · 음성)에는 ROS가 없다. 로봇 PC의 `bridge` 노드가 웹 쪽 토픽 · 서비스를 **대신** 한다 — 로봇 PC 노드는 웹이 ROS 노드인 것처럼 `/d2/hmi/…` 이름을 그대로 쓴다. 규칙은 [10장](#10-pc-사이-통신--mqtt-다리-e-27e-30). 토픽은 `d2/<ROS 이름>`, 서비스는 `…/req` · `…/res` + `req_id`.

- **돌리는 곳(E-26 · E-31):** **웹 PC**(ROS 없음) = 컨테이너 `mosquitto` · `db` · `web`(안, 호스트도 됨) + 호스트 음성. **로봇 PC** = 모두 호스트(브링업 · 집기 · 놓기 · 장면 · 그리퍼 · 정지 · 손목 블록 인식 + 스캔 추론기 · **task** · **bridge**). 컨테이너 `hmi` · `db-hmi`는 없다. ROS 2(CycloneDDS 60)는 로봇 PC 안에서만.
- **기록기 노드는 없다.** 작업 관리자가 CSV를 쓰고, 핵심에서 같은 칸을 `builds`로 넘긴다(HMI `design_store`가 DB에 씀 — 넘기는 길 = `/d2/hmi/save_build`, 4.2 · 정함 ⓐ).
- 실행 이름(안)은 담당이 바꿀 수 있고, 바꾸면 이 표를 고친다.

## 4. 통신 표

> 아래 이름은 **로봇 PC 안의 ROS 약속**이다. '화면 · 음성'이 보내거나 받는 것은 **실제로는 다리 노드 `bridge`가 그 자리에서** 보내고 받는다(E-28). 웹 PC와 오가는 MQTT 토픽은 [10장](#10-pc-사이-통신--mqtt-다리-e-27e-30)의 표 하나로 정한다 — 이 장의 이름 · 칸이 바뀌면 10장도 같이 바뀐다.

### 4.2 서비스

| 이름 | 형식 | 부르는 쪽 → 답하는 쪽 | 언제 | 요청 → 결과 |
|---|---|---|---|---|
| `/d2/hmi/command` | `d2_interfaces/HmiCommand` | 화면 → 작업 관리자 | 버튼 | cmd(`select_design` · `start` · **`scan`** · **`cancel`**), design_id, mode(`auto` 또는 빈 값) → success, reason. `scan` = 스캔 흐름 시작(작업 관리자가 SCAN_MOVE로, `SCAN_REVIEW`에서는 다시 스캔). `WAIT_SUPPLY` · `WAIT_HMI`에서 `start` = [계속]. `cancel` = `SCAN_REVIEW` 취소 → IDLE(10/7 PL) **늦은 실행 금지(10/7 PL):** 작업 관리자는 명령을 받은 순간부터 `timeout.command_s`(4초 — 화면이 기다리는 `mqtt.req_timeout_s` 5초보다 먼저) 안에 확정하지 못하면 **실행하지 않고 `TIMEOUT`으로 답한다** — 화면은 실패인데 로봇이 늦게 출발하는 일을 막는다. [출발]은 [설계 선택] 때 받아 둔 설계를 쓴다(같은 design_id면 다시 조회하지 않음, 권장) |

| **`/d2/hmi/save_build`** (정함 ⓐ) | `JsonQuery` | 작업 관리자(RunLogger) → 웹 backend(design_store) | 조립이 끝날 때(DONE · STOPPED 뒤 그만둠 · ERROR) | `build/1`(6장) → `{"ok"}`. 조립 결과 저장 — 기록 주인은 작업 관리자, DB 쓰기는 HMI. **두 층(10/7 PL):** 서비스 `success` = 요청을 받아 처리함, 응답 JSON `ok` = DB에 저장됨(DB 쓰기 실패면 `success: true` · `ok: false` + 이유). 작업 관리자는 **둘 다 참일 때만** 저장됐다고 보고, 아니면 요약을 남겨 다시 보낸다(PR #40) → **웹 backend는 같은 `run_id`가 다시 오면 한 번만 저장하고 `ok: true`로 답한다** |

AI가 쓴 칸(role · part · stage · grasp)이 빠지거나 틀리면(이름 형식 · 같은 부품 블록이 맞닿아 이어짐 · 단계 규칙 · 잡기가 놓인 자세와 맞음 · 손가락 자리 · 공중 블록 없음) `ok: false` + `CHECK_FAILED` — 변환기 ①이 대신 채우지 않고 HMI가 재생성(최대 2번). 웹은 합격한 설계(AI 생성은 사람이 고른 후보 1개 — 10/8 E-67)의 이 둘과 blocks를 `design/2.0`으로 저장한다(E-59 → 10/8 E-69). 검사 불합격은 서비스 `success: true` + `ok: false`. 변환기 ①은 task 검사 묶음에 붙었다(W110 — #99 본체 · #100 검사 묶음 연결, 10/8 밤). 변환기 ①이 찾은 AI 칸 실수(역할 · 옵션 목록 밖 · 같은 부품이 면으로 안 맞닿음 · 고른 잡기 불가)는 `ok: false` + `errors[].reason` `CHECK_FAILED`(재생성), 그 밖의 변환기 예외는 `success: false` · `ERROR`. 3초 목표, 시간 제한 5초(7장 `TIMEOUT`) |

## 6. JSON 형식

### 형식 버전 규칙 (10/8 E-69, PL · 한세교)

- 형식 이름 = `<이름>/<앞>.<뒤>`(예 `recipe/2.0`). 형식 버전은 '어떤 규칙으로 읽는지'의 표시다 — 설계 내용 버전(DB 트리 v1.0 → v1.1) · git 이력과 다르다.
- **앞자리 +1(뒤 0) = 깨지는 변경** — 칸의 뜻 · 필수 칸 더하거나 뺌 · 칸 이름 · 타입 · 단위 바뀜 → 읽는 쪽 코드를 고친다. **뒷자리 +1 = 호환 확장** — 선택 칸 더함 → 안 고쳐도 된다.
- 읽는 쪽: 앞자리가 같으면 받고 모르는 칸은 무시, 앞자리가 다르거나 이름이 다르면 거절(이유에 받은 `schema`). 내용 확인은 칸 이름이 아니라 `schema`로.
- 짝 형식(`recipe` · `placements`)은 같은 숫자로 함께 올린다. 점 없는 이름(`state/1` · `intent/1` · `build/1` 등)은 다음에 바뀔 때 `<앞>.<뒤>` 꼴로 옮긴다 — 첫 예: `progress/1` → `progress/1.1` · `scan_result/1` → `scan_result/1.2`(10/9 E-75, `stamp` 칸 더함 = 호환 확장).
- 이번에 적용: `cad_structure/1.0` → `recipe/2.0`, `cad_recipe/1.0` → `placements/2.0`, `blocks/1` → `blocks/2.0`(필수 칸 추가 — 깨지는 변경, `blocks/1`은 스캔 추론기 출력으로 남음), `design/1` → `design/2.0`, `check_result/1` → `check_result/2.0`. 옛 형식으로 저장된 생성 · 시험 설계는 거절(변환하지 않음), 기본 4종은 새 파일로 다시 등록.

## 8. 호출 순서

> 이름은 ROS 이름이다. 화면 · 음성 ↔ 작업 관리자 · 정지 노드 사이는 **다리를 거친다**(화면(frontend) → REST → backend → MQTT `…/req` → 다리 → ROS 서비스 → 답 → `…/res` → backend → 화면 — E-41). 순서 · 뜻은 같다.

### 8.1 저장된 설계 조립 — 블록 1개 (1차 자동 모드와 같음)

```text
①  화면·음성  → hmi/command {cmd: select_design, design_id}  또는 hmi/intent {intent: select_design}  → 작업 관리자
②  작업 관리자 → hmi/get_design {design_id}                     → 웹 backend(design_store): design/2.0 답(recipe · placements · blocks — 10/8 E-69)  (웹 없이 개발 때는 design_source:=local로 레시피 두 파일 직접)
③  화면·음성  → hmi/command {cmd: start} 또는 hmi/intent {intent: start}                              → 작업 관리자: 시작 점검(로봇·그리퍼·카메라·DB·조립 자리 비었나·공급) → 출발
④  작업 관리자 → motion/move_to {target: observe}              → 집기·놓기 (다 간 뒤 답)
⑤  작업 관리자 → vision/check_progress {block_ids}              → 손목 블록 인식
⑥  작업 관리자: 답을 작업 판단(TaskPlanner)에 → task/progress (진행표) → 장면 관리·화면
⑦  작업 판단: 다음 블록 = sequence 첫 미배치 (함수 호출) → {block_id, supply_slot, pick_pose, place_pose, grasp} / DONE
    (핵심, 흩뿌림) 작업 관리자 → motion/move_to {target: observe_supply} → vision/find_blocks {run_id} → 작업 판단이 가장 잡기 쉬운 블록을 골라(E-46) pick_pose · grasp · open_width_m을 채움, supply_slot은 빈 값
⑧  작업 관리자 → motion/pick_place (액션)                       → 집기·놓기: approach → gripper/command → scene/attach true → lift·move·place → attach false → retreat → 결과
⑨  (1차) SLOT_EMPTY가 이어져 공급이 다 비면 → WAIT_SUPPLY + 알림 supply_empty → 사람이 채우고 [계속] 버튼(= start) → ⑧부터
    (핵심, 흩뿌림) 공급 영역 관측 자세에서 vision/find_blocks에 블록이 0개면 → WAIT_SUPPLY + supply_empty → 사람이 놓고 [계속](= start) → find_blocks부터 다시
⑩  ④로 돌아가 블록마다 배치 확인 → 다 놓이면 DONE → RunLogger: CSV + hmi/save_build {build/1}(HMI가 builds에 씀) → 알림 done
```

### 8.2 정지 (바뀐 곳: 서기 궤적이 토픽, 웹캠 없음)

```text
①  화면 정지 버튼·키 → safety/stop {source, reason}  → 정지 노드 → 답 success   (Ctrl+C는 움직이는 프로그램이 스스로 서기 궤적)
②  정지 노드: 멈출지 판단 — 정지 입력 / 로봇 알람 / 시간 초과(작업 관리자 요청)   (그리퍼 응답 없음 · ERROR는 작업 관리자 ERROR — 10/9 E-74, 카메라 연결 끊김 → 정지는 나중에)
③  정지 노드 → 토픽 /dsr_moveit_controller/joint_trajectory (서기 궤적: 지금 관절값, 0.3초)   ← 액션 아님(10/6 박진용)
④  정지 노드 → safety/state {stopped: true, locked: true, reason: STOP_WEB|ROBOT_ALARM:<상태>|…}  → 작업 관리자 STOPPED, 화면 "멈췄어요", 집기·놓기 목표 취소(CANCELED)
⑤  사람 확인 → 화면 '다시 시작' → safety/resume → 잠금 풀림 → 작업 관리자가 바로 관측부터(8.1 ④ — 첫 move_to는 speed_ratio 0.5, W121 C-1)
```

- 펜던트 비상정지 · 두산 충돌 감지는 늘 작동. 2초 안에 안 서면 `move_stop`, 그래도 안 서면 펜던트.
- 다시 시작 버튼 옆에 '로봇 작업 영역에서 손을 빼고 누르세요'(HMI).

### 8.3 설계 생성 — AI가 설계도를 직접 쓰고 사람이 후보를 고른다 (새, 핵심 · 10/8 E-67 · E-69) — HMI 안에서 돌고 검사만 task를 부른다

```text
①  웹 글상자 [생성](frontend → REST /api/designs → backend)  또는  음성 → hmi/intent {intent: request_design, text}  → backend → /ws → 화면: 문장을 보여 주고 사람이 [생성] 확인 (E-07)
②  design_gen: design_store 목록 요약(design_id · family · version · parent_id · made_by · 블록 수 · 외곽 · 최근 builds 결과)을 GPT에 줌 → GPT가 참고할 설계를 도구 get_design(design_id)으로 골라 읽음(최대 2번) (RAG — 10/9 E-72)
    도구를 안 부르거나 실패하면 코드가 같은 family의 기본 설계·파생본(최근 3)·builds 결과(examples_for)를 넣는 길로 자동 전환
③  design_gen → GPT-4o 한 번 호출로 **후보 3개**(10/8 E-67) — ②에서 읽은 설계를 예시로 보고(E-11 · E-72) 블록마다 위치 · 방향 · 순서(order) · role · part · stage · grasp 를 직접 씀(JSON Schema blocks/2.0 × 3) → blocks/2.0 × 3   (10/8 E-69 — 템플릿 길 `build_template`은 없앰)
    역할 · 옵션 이름은 저장소 JSON 파일(목록)을 프롬프트에 먼저 주고 맞는 것이 있으면 그것을 쓴다. 잡기 규칙(한세교 7-3 — 닫는 방향 양옆 블록이 가까우면 그 방향은 못 잡음, 둘 다 되면 짧은 쪽)도 프롬프트에
    가구 2종 밖·범위 밖 → OUT_OF_SCOPE → 화면 안내, 끝
④  화면(frontend): 후보 3개를 3D 미리보기(three.js, E-40)로 나란히 + "디자인을 고르세요".  그 뒤에서 design_gen → task/check_design {blocks/2.0}을 후보마다 한 번씩(3번, 요청 · 응답 칸은 그대로)
    → DesignChecker: 안정성(7 mm, 쌓는 도중) + 받침·틈·잡기·막힌 칸·작업영역 + AI 칸 검사(이름 형식 · 같은 부품 블록 맞닿음 · 단계 규칙 · 잡기 · 손가락 자리 · 공중 블록 — 빠지거나 틀리면 CHECK_FAILED, 코드가 대신 채우지 않음) → ok면 변환기 ①이 번호 · 중심 · R · 받침 · 닫힘 축을 계산해 recipe + placements.  불합격 후보는 화면에서 회색(고를 수 없음)
⑤  3개 다 불합격이면: errors[].detail을 LLM 피드백으로 → ③부터 다시 (최대 2번) → 그래도 실패 → GEN_FAILED → 화면 이유 + 기본 설계 권함
⑥  사람이 합격 후보 1개를 고름 → 화면 "설계도 만드는 중" → design_store.save_design(designs: parent_id(= ②에서 GPT가 읽은 설계 — 둘이면 처음 것, 자동 전환이면 기본 설계 · E-72), version +0.1, made_by, prompt, blocks, 그 후보의 검사 결과 recipe · placements, check)
    → 안 고른 후보 2개는 designs에 rejected 기록만(트리 · 출발 대상 아님) → 화면: 블록 수 · 검사 결과 · 버전 트리 → 알림 ready_to_start
⑦  사람이 [출발] → 8.1 ③부터 (작업 관리자는 get_design으로 design/2.0 — recipe + placements를 받음)
```

- ①~⑥은 로봇이 움직이지 않는다. 작업 관리자 상태는 IDLE/READY 그대로이고, 화면 알림만 `state/1`에 싣거나 화면이 직접 띄운다(HMI 안).
- 요청 → 후보 3개 미리보기까지 제안 ≤ 60초(검사 3번은 미리보기 뒤에서). 10/8 E-69: 후보 3개 × 칸 9개라 AI가 틀리면 실패가 늘 수 있음 — W108 시험(요청 15개)에서 통과율 · 시간을 다시 잰다. 생성 중 표시 `generating`. 고른 뒤 저장 중 표시 "설계도 만드는 중".

### 8.4 스캔 복제 (새, 핵심 10/10~12)

```text
①  사람: 완성한 구조물을 조립 작업영역에 두고 나감 → 화면 [스캔] → hmi/command {cmd: scan}  → 작업 관리자: SCAN_MOVE (시작 점검: 그리퍼 빔 — 사람이 영역 밖인 것은 누르는 사람이 확인)
②  작업 관리자 → motion/move_to {target: observe}        → 집기·놓기 → 작업 관리자 → vision/scan_capture {pose_id: observe}        (SCAN_CAPTURE)
③  작업 관리자 → motion/move_to {target: observe_front}  → … → vision/scan_capture {pose_id: observe_front}
④  (선택) observe_side 도 같은 순서
⑤  작업 관리자 → vision/scan_infer {run_id}               → StructureScanner: 점군 → base_link → 작업면 위 높이 지도 → 격자(15·25·75 / 25·75 mm) → 블록 자리·방향 → 가려진 블록 받침 규칙으로 추정(inferred) → blocks/1(위치 · 방향 + inferred만 — `order`는 블록 번호일 뿐 조립 순서로 안 씀, 10/8 E-69) + cloud_path(PLY, 선택)   (SCAN_INFER)
⑥  작업 관리자 → task/scan_result {blocks, inferred_count, image_path, cloud_path(선택 — 10/8 E-67)}  → 화면: 실물 사진 ↔ 추론 설계 비교, 추정 블록 표시, 점군 창(cloud_path 있을 때)   (SCAN_REVIEW)
⑦  사람이 비교 화면에서 [저장] → 화면(HMI): design_gen이 GPT-4o로 blocks/1에 역할 · 부품 · 순서 · 단계 · 잡기(role · part · stage · grasp)를 채움(추측 표시 inferred를 힌트로, 10/8 E-69) → blocks/2.0 → task/check_design {blocks/2.0}  → ok → design_store.save_design(made_by: scan, parent_id · family: 같은 GPT 호출에서 AI 생성과 같은 방식(E-72)으로 DB 목록 요약을 보고 도구 get_design으로 고른 가장 비슷한 설계 — DB 전체 후보(기본 · 파생 · 예전 스캔), 모양(blocks/1 위치 · 방향)은 안 바꿈, 부모는 같은 family만(다르면 버리고 같은 family의 가장 비슷한 기본 설계), GPT 실패 땐 scan_result의 nearest_base — 10/9 E-79) — 저장은 [저장]을 누를 때만(10/7 21시 PL, E-56). [다시 스캔] · [취소]는 ⑧
⑧  SCAN_REVIEW 끝내기: 저장 → hmi/command {select_design, 새 design_id} → READY(→ [출발] = start로 복제) · 다시 스캔 → {scan} → SCAN_MOVE · 취소 → {cancel} → IDLE
⑨  사람: 구조물을 치움 → [출발] → 8.1 ③부터 (같은 조립 원점에 복제) → 끝나면 builds에 복제 결과(일치율·오차)
```

- 스캔 중 로봇은 카메라만 움직인다(블록을 잡지 않음). 사람이 영역 밖인 것은 [스캔]을 누르는 사람이 확인(SR-07).
- ⑦의 검사 · 저장은 생성 흐름(8.3 ④~⑥)과 같은 코드다. GPT가 선택 값을 채우는 것도 design_gen 한 곳(E-69).
- **비교 화면 버튼(10/9 E-80):** [그대로 저장] — ⑦ · **[AI로 고치기]**(챌린지 W125 — 요청 문장은 비워도 됨 → 스캔 저장본을 부모로 8.3 생성 흐름 → 후보 3개 → 사람이 고름) · [다시 스캔] · [취소]. 스캔마다 AI 후보를 자동으로 만들지 않는다(핵심 W116 스캔 복제가 GPT 시간 · 비용에 묶이지 않게).

## 10. PC 사이 통신 — MQTT 다리 (E-27~E-30)

웹 PC에는 ROS 2가 없다. **로봇 PC의 `bridge` 노드 하나**가 ROS ↔ MQTT를 바꾸고, 웹 PC의 **Mosquitto 브로커**(컨테이너 `mosquitto`, 1883)가 가운데 선다. 웹 백엔드(backend, FastAPI) · 음성은 paho-mqtt로 브로커에 붙는다. 브라우저(frontend) ↔ backend는 REST(`/api/designs` · `/api/robot`) + WebSocket `/ws`(브라우저는 브로커에 직접 붙지 않는다, E-41). **아래 표의 '웹'은 backend · 음성**이다. 로봇 PC 안은 10/4 그대로다(CycloneDDS, `ROS_DOMAIN_ID` 60 — [env/README](env/README.md) 6장).

### 10.1 토픽 표 — ROS ↔ MQTT

| ROS 이름(4장) | MQTT 토픽 | 방향 | MQTT payload | retained | QoS |
|---|---|---|---|---|---|
| `/d2/task/state` | `d2/task/state` | 로봇 → 웹 | `state/1` JSON 글자 그대로 | ✅ | 1 |
| `/d2/task/progress` | `d2/task/progress` | 로봇 → 웹 | `progress/1.1` 그대로 | ✅ | 1 |
| `/d2/task/scan_result` | `d2/task/scan_result` | 로봇 → 웹 | `scan_result/1.2` 그대로 | ✅ | 1 |
| `/d2/safety/state` | `d2/safety/state` | 로봇 → 웹 | `safety_state/1` 그대로 | ✅ | 1 |
| `/d2/gripper/state` | `d2/gripper/state` | 로봇 → 웹 | `gripper_state/1` 그대로 | ✅ | 0 |
| `/d2/hmi/intent` | `d2/hmi/intent` | 웹(음성) → 로봇 | `intent/1` 그대로 — 다리가 ROS 토픽으로 낸다 | ✗ | 1 |
| `/d2/hmi/command`(서비스) | `d2/hmi/command/req` → `d2/hmi/command/res` | 웹 → 로봇 → 웹 | req `{"req_id","cmd","design_id","mode"}` → res `{"req_id","success","reason"}` | ✗ | 1 |
| `/d2/safety/stop`(서비스) | `d2/safety/stop/req` → `…/res` | 웹 → 로봇 → 웹 | req `{"req_id","source","reason"}` → res `{"req_id","success","message"}` | ✗ | 1 |
| `/d2/safety/resume`(서비스) | `d2/safety/resume/req` → `…/res` | 웹 → 로봇 → 웹 | req `{"req_id"}` → res `{"req_id","success","message"}` | ✗ | 1 |

| `/d2/hmi/get_design`(JsonQuery, 로봇이 부름) | `d2/hmi/get_design/req` → `…/res` | 로봇 → 웹 → 로봇 | req `{"req_id","design_id"}` → res = `design/2.0` 객체(10/8 E-69) + `req_id` · `success` · `reason` | ✗ | 1 |
| `/d2/hmi/save_build`(JsonQuery, 로봇이 부름, 정함 ⓐ) | `d2/hmi/save_build/req` → `…/res` | 로봇 → 웹 → 로봇 | req = builds 칸 + `req_id` → res `{"req_id","success","reason","ok"}`(`ok` = DB에 저장됨, 4.2 — 10/7 PL) | ✗ | 1 |
| (없음) | `d2/bridge/alive` | 로봇 → 웹 | `{"alive":true,"stamp"}` 1초마다, LWT `{"alive":false}` | ✅ | 1 |
| `/d2/hmi/alive` | `d2/web/alive` | 웹 → 로봇 | 같음 — 다리가 ROS 토픽으로 낸다 | ✅ | 1 |
| (없음, 정함 10/8 E-67) | `d2/vision/scan_image` · `d2/vision/scan_cloud` | 로봇 → 웹 | JPEG 바이트(≤ 500 KB) · 다운샘플 PLY 바이트(복셀 3 mm, ≤ 2 MB) — 다리가 `scan_result`의 `image_path` · `cloud_path` 파일을 읽어 보냄 | ✗ | 1 |
| `/d2/vision/wrist_image` (정함 10/8 E-67) | `d2/vision/wrist_image` | 로봇 → 웹 | JPEG 바이트(`CompressedImage.data`, 640×480 · 약 65 KB, 1~2 Hz) | ✗ | 0 |

- **규칙:** 토픽 = ROS 이름에서 맨 앞 `/`만 뺌. 상태(JSON 토픽)는 payload를 **그대로**(std_msgs/String 내용 = payload). **retained**는 ROS의 TRANSIENT_LOCAL 자리다 — 화면이 늦게 붙어도 마지막 상태를 받는다.
- **서비스 = `…/req` · `…/res` + `req_id`(UUID4).** 요청 payload = ROS 요청 칸들을 JSON 객체로(JsonQuery는 `request_json`의 객체 자체) + `req_id`. 응답 = ROS 응답 칸(+ JsonQuery는 `response_json`의 객체를 펼침) + `req_id`. 응답을 `mqtt.req_timeout_s`(5초) 안에 못 받으면 `TIMEOUT` — **웹은 시간 초과 때 자동으로 다시 보내지 않고 실제 상태는 `state/1`(retained)로 보여 준다.** 로봇 쪽은 `timeout.command_s`(4초)로 늦은 실행을 막는다(10/7 PL). 같은 `req_id`가 두 번 오면 두 번째는 버린다.
- **다리는 변환만 한다.** 판단(멈출지 · 진행표 · 설계 검사)은 하지 않는다. 다리가 죽어도 로봇 PC 안 정지(키 · Ctrl+C · 알람 · 펜던트)는 그대로다(E-30 ⓑ).
- 이름 · 칸이 4~6장에서 바뀌면 이 표도 같이 바꾼다(payload는 같은 JSON이라 다리 코드는 대개 안 바뀜).
