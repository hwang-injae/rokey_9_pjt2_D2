## 1. 먼저 범례(그림 맨 위)

- **① 화살표 색 = 데이터 갈래 7개:** 파랑 **명령**(화면 · 음성 → 다리 → 작업 관리자) · 보라 **표시**(작업 관리자 · 그리퍼 → 다리 → 화면) · **주황 설계**(생성 · 검사 `check_design` · 설계 꺼내기 `get_design` · 저장 — 블록 JSON · 레시피가 오가는 길) · 초록 **관측 · 스캔 · 진행표** · 검정 **동작** · 빨강 **정지** · 회색 **장치 · 바깥 · 생존 신호**(USB · 제어기 · OpenAI · `alive`).
- **② 선 모양:** 실선 = 1차 · 핵심(10/13 동결까지). 점선 = 챌린지에 붙일 연결(카메라 끊김 → 정지, 음성 '멈춰'). 다리(반원) = 선이 겹치는 곳.
- **③ 상자 종류:** 노드 카드(머리띠 색 = 파트: 주황 HMI · 초록 비전 · 파랑 로봇 동작) · 이미 있는 노드(브링업) · 챌린지 노드(점선) · **저장소(DB · MQTT 브로커) · 라이브러리(레시피 도구)** · 장치 · 컨테이너(파란 점선 큰 상자: `web` · `mosquitto` · `db` — 모두 웹 PC) · 클래스(카드 안 회색 묶음).
- **④ 낱말:** 노드 · 패키지 · 클래스 · 컨테이너 · **MQTT · 다리** · 블록 JSON · 레시피 · 토픽 · 서비스 · 액션.
- **그림에서 `MQTT …`로 시작하는 입력 · 출력**은 웹 PC ↔ 로봇 PC 사이를 오가는 것이다. 화살표는 논리 연결로 그렸지만 **실제로는 전부 웹 PC의 브로커(`mosquitto`)를 거친다.**

## 3. 큰 그림 — 가로 띠 3개

위 **웹 PC** 띠(ROS 없음 — 컨테이너 3개 + 호스트 음성) → 가운데 **로봇 PC** 띠(ROS 노드 전부, 호스트) → 아래 **장치 · 바깥 서비스** 띠(사람 · OpenAI · 마이크 · 카메라 · 제어기 · 그리퍼). **두 PC 사이를 잇는 것은 다리 노드 하나**다. 웹 PC → 로봇 PC로 가는 것은 다섯 갈래(명령 · 의도 · 검사 · 정지 · 다시 시작), 로봇 PC → 웹 PC는 상태 토픽 5개 + 설계 꺼내기 · 조립 기록 요청 + 사진 · 점군(안). **생성 · 저장은 웹 PC 안에서, 검사는 로봇 PC(task)에서 끝난다.**

## 4. 카드 하나를 읽는 법 — v2와 같음

왼쪽 **입력**(받는 것) → 가운데 **처리**(번호 순, 클래스 묶음) → 오른쪽 **출력**(내보내는 것). 카드 안 가는 선은 어느 입력이 어느 처리로 가고, 어느 처리가 어느 출력을 내는지다(색 = 들어온 화살표 색). 예: **bridge 카드** — 입력 `MQTT …/req`는 ① ROS 서비스 호출 → 출력 `/d2/hmi/command · …(서비스 부름)`과 `MQTT …/res`. 입력 `/d2/task/state · …(토픽)`은 ④ → 출력 `MQTT d2/task/state · …(retained)`.

## 6. 자주 묻는 것

- **왜 PC 사이를 ROS 2가 아니라 MQTT로?** 웹 PC에 ROS · 두산 환경을 깔지 않아도 되고, 강의실 망의 DDS 멀티캐스트 문제가 없고, `mosquitto_sub -t 'd2/#' -v` 한 줄로 PC 사이 모든 메시지를 볼 수 있다(E-27). 로봇 PC 안은 그대로 ROS 2다.
- **MQTT에는 서비스가 없는데 명령 · 검사 · 설계 꺼내기는?** 요청 토픽 `…/req`와 응답 토픽 `…/res`를 짝으로 두고 `req_id`로 맞춘다. 5초 안에 답이 없으면 `TIMEOUT`(E-29, IRD 10장).
- **ROS 쪽 코드가 바뀌나?** 안 바뀐다(E-28). task · 비전 · 로봇 동작은 `/d2/hmi/…` 이름을 그대로 쓰고, 그 자리에 다리가 선다. 가짜 노드 `mock_web_ui`는 이름만 `mock_bridge`로.
- **브로커 · 다리가 죽으면?** 화면만 끊긴다. 로봇 PC의 정지(키 · Ctrl+C · 알람 · 펜던트)는 그대로이고, 화면은 `d2/bridge/alive`가 끊기면 "연결 끊김"을 크게 띄운다. 조립 중 웹이 끊기면 task는 현재 블록까지 놓고 기다린다(안).
- **AI가 만든 설계가 이상하면?** 검사 묶음(③④)이 거르고, 통과해도 사람이 미리보기를 보고 [출발]을 눌러야 로봇이 움직인다(SR-09). 생성 직후 자동 출발은 없다.
- **왜 검사는 web이 아니라 task에?** 쌓을 만한지는 로봇 쪽(작업 판단)이 가장 잘 알고, 변환기 ①(레시피 도구)을 바로 부를 수 있어서. 웹 PC ↔ 로봇 PC 사이는 요청 한 번(`check_design/req` → `…/res`)이다.
- **DB는 어디서 읽나?** web(DesignStore) 한 곳. task는 `get_design` · `save_build` 서비스(다리 제공)로만. W088 전에는 JSON 파일 폴더로 돈다.
- **사람 감지는?** 웹캠을 빼서 없다(E-19). [출발] · [스캔] · [계속]을 누르는 사람이 영역 밖인지 확인한다. 카메라 신호 끊김 → 정지는 챌린지(점선).
- **공급 칸이 비면?** `SLOT_EMPTY`가 모든 칸 → task WAIT_SUPPLY → 화면 "공급 채워 주세요" → 사람이 채우고 [계속] 버튼(= `start`).
- **인터넷이 끊기면?** 생성 · 음성 분류가 안 된다. 저장된 설계 조립(⑥~⑪)은 된다.

## 7. 설명 번호 ↔ task 상태 이름

| 번호 | task 상태 | 비고 |
|---|---|---|
| ①~⑤ | IDLE / READY(그대로) | 생성 · 검사 · 저장은 웹 PC 안 상태(`GENERATING` → `CHECKING` → `SAVED`), task는 검사만 답한다 |
| ⑥ | IDLE → READY | `get_design`(다리 경유) |
| ⑦ | READY → CHECK | 시작 점검(다리 연결 포함) |
| ⑧ | CHECK | 관측 · 진행 확인 |
| ⑨ | SELECT | 다음 블록 |
| ⑩ | PICK_PLACE → VERIFY → (SELECT) / WAIT_SUPPLY | 블록마다 |
| ⑪ | DONE → IDLE | save_build |
| ⑫~⑭ | STOPPED → RECOVER → CHECK(또는 IDLE) | 어느 상태에서나 |
| ⑮ | IDLE → SCAN_MOVE | [스캔] |
| ⑯ | SCAN_MOVE ↔ SCAN_CAPTURE → SCAN_INFER | 자세마다 |
| ⑰ | SCAN_REVIEW → IDLE | 저장 · 다시 스캔 · 출발은 화면에서 |

## 8. 그림이 IRD와 다른 곳 · 아직 '안'인 것

- 그림의 새 이름(`JsonQuery` · `check_design` · `get_design` · `save_build` · `scan_capture` · `scan_infer` · `scan_result` · `scan` 명령 · `request_design` 의도 · 촬영 자세 2개)과 **MQTT 토픽 규칙 · `req_id` · 생존 신호 · `mqtt.*` 키**는 IRD v3에 **'안'** 으로 들어 있고 **10/7 오전 W121**에서 확정한다. 확정 전에는 IRD v3 이름을 그대로 쓴다.
- **다리 노드 담당**은 안 황인재(대안 박진용) — W121에서 정한다(E-33). 그림은 HMI 머리띠로 그렸다.
- `save_build`(task → 다리 → web, 조립 결과를 DB로)는 IRD 12장의 안 ⓐ다. ⓑ(web이 state · progress를 구독해 스스로 기록)로 정하면 이 화살표가 없어진다.
- 레시피 도구의 패키지 이름 · 위치는 로봇 동작(한세교)이 정한다. 그림은 '라이브러리' 상자로만 그렸다(로봇 PC).
- 스캔 사진 · 점군을 화면에 보내는 방법은 **다리가 MQTT 바이너리 토픽으로**(안) — 크기 · 다운샘플 간격은 10/9.
- 그림의 MQTT 화살표는 web ↔ bridge를 직접 잇는 것처럼 그렸지만 모두 `mosquitto`를 거친다. 브로커 상자에 화살표를 따로 긋지 않았다.
