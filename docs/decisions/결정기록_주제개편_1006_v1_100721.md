## 6. R-11 설명 — 왜 MongoDB인가 **(→ 10/6 21시 E-39: PostgreSQL 16으로 정함 — 이 절은 참고로 남김)**

- **설계가 JSON 문서다.** 블록 목록 길이가 설계마다 다르고(9~25개), 칸이 자주 바뀐다(검사 결과 · 프롬프트 · 버전 · 스캔 사진 경로). **문서형 DB는 이 JSON을 그대로 넣고 그대로 꺼낸다** → 코드가 짧고 칸을 더해도 표를 고칠 일이 없다.
- **관계형(SQL)이면** 설계 표 + 블록 표를 나누어(설계 1개 = 블록 행 11~25개) 합쳐 읽거나, JSON 칸(PostgreSQL JSONB)을 써야 한다. 되긴 하지만 손이 더 간다.
- **버전 트리(`parent_id`) · 조립 결과 기록은 어느 DB든 된다.** 차이는 JSON 다루기 편의뿐이다.
- **스크립트 ②가 NoSQL(MongoDB)을 명시**해 발표 서사("NoSQL 기반 경량 PLM")와 맞고, 평가 힌트 "컨테이너 + DB"에는 어느 DB든 해당한다.
- **설치:** Docker 공식 이미지 1줄, Python `pymongo`. 두 PC에서 같이 접근 가능(서버형).

| 후보 | 장점 | 단점 | 평 |
|---|---|---|---|
| **MongoDB** | JSON 그대로, 칸 추가 자유, 서버형(PC 2대), 스크립트와 일치 | 팀에 경험 없으면 쿼리 문법 익힘(반나절) | **추천** |
| PostgreSQL(JSONB) | SQL 익숙한 팀원이 있으면 편함, JSON 칸도 됨 | 표 설계 · 설정이 조금 더 | 팀원이 SQL을 잘 알면 대안 |
| SQLite | 파일 하나, 설치 없음 | 서버가 아니라 두 PC 동시 접근 어려움, '컨테이너 DB' 요소가 약함 | 비추천 |

→ **팀에 MongoDB · SQL 경험자가 누구인지에 따라 정하면 된다.** 경험이 비슷하면 MongoDB.
