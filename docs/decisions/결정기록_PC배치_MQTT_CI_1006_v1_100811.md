## 1. PC 배치

| 번호 | 결정 | 내용 · 이유 |
|---|---|---|
| **E-26** | **PC 2대 = 웹 PC + 로봇 PC.** 웹 PC(옛 '운영 PC')에는 **웹 화면 · AI 설계 생성 · 저장소 · DB · MQTT 브로커 · 음성**만 두고 **ROS 2를 깔지 않는다.** 로봇 PC에는 **ROS 2 노드 전부**(브링업 · 집기 · 놓기 · 장면 · 그리퍼 · 정지 · 손목 블록 인식 + 스캔 추론기 · **작업 관리자 + 작업 판단 + 검사 묶음(task)** · **다리 노드 bridge**)를 둔다 | PL 10/6 18시. task(검사 묶음 포함)가 운영 PC → 로봇 PC로 옮겨 간다. 레시피 도구(변환기 ①)도 task가 import 하므로 로봇 PC |
| **E-27** | **PC 사이 통신 = MQTT.** 웹 PC에 **Mosquitto 브로커**(1883), 로봇 PC에 **다리 노드 `bridge`**(rclpy + paho-mqtt — ROS ↔ MQTT 변환). ROS 2(CycloneDDS, 도메인 60)는 **로봇 PC 안에서만** 쓴다. 웹 백엔드(FastAPI)는 paho-mqtt로 브로커에 붙는다. 브라우저 ↔ 웹 백엔드는 지금처럼 WebSocket | PL 10/6 18시. 이유: 웹 PC에 ROS · 두산 환경을 깔 필요가 없고, PC 사이 DDS 멀티캐스트 문제(강의실 망)에서 벗어난다. `mosquitto_sub -t 'd2/#' -v` 한 줄로 PC 사이 모든 메시지를 볼 수 있어 디버깅이 쉽다 |
| **E-28** | **ROS 쪽 인터페이스(IRD 4장)는 바꾸지 않는다.** 로봇 PC 노드가 보기에 웹 화면 · 음성은 **다리 노드가 대신한다** — 다리가 `/d2/hmi/command` · `/d2/task/check_design` · `/d2/safety/stop` · `resume`을 **부르고**, `/d2/hmi/get_design` · `/d2/hmi/save_build`를 **제공하고**, `/d2/hmi/intent`를 **내고**, `task/state` · `progress` · `scan_result` · `safety/state` · `gripper/state`를 **받아 MQTT로 넘긴다.** 그래서 task · 비전 · 로봇 동작 코드와 가짜 노드(mock)는 그대로다 | 조립 엔진 · 작업 관리자를 건드리지 않는다. 바뀐 것은 HMI 쪽(웹 코드 + 다리) |
| **E-29** | **MQTT 다리 규칙(안, IRD v3 10장):** **(→ 10/7 13시 W121: '임시 정함' → 10/8 '정함'(E-57))** ① 토픽 이름 = ROS 이름에서 맨 앞 `/`만 뺌(`d2/task/state`) ② 상태 토픽은 JSON 글자 그대로(std_msgs/String 내용 = MQTT payload), **retained**(화면이 늦게 붙어도 마지막 상태를 받는다 — TRANSIENT_LOCAL 대신) ③ 서비스는 **요청 토픽 `…/req` · 응답 토픽 `…/res` + `req_id`**(JSON 칸, UUID). 요청 payload = ROS 요청 칸들을 JSON 객체로(JsonQuery는 `request_json`의 JSON 객체 자체) + `req_id`; 응답도 같은 꼴 + `success` · `reason` ④ QoS 1 ⑤ **생존 신호** `d2/bridge/alive` · `d2/web/alive` 1초마다 + LWT(끊기면 `{"alive":false}`) → 화면은 "로봇 PC 연결 끊김"을 띄우고 [출발]을 막는다 ⑥ 사진 · 점군은 바이너리 토픽(`d2/vision/scan_image` JPEG · `d2/vision/scan_cloud` 다운샘플 PLY, 안) — 파일 경로 대신 내용을 보낸다 | MQTT는 요청-응답이 없어 토픽 두 개 + 번호로 만든다. mqtt_client(apt `ros-jazzy-mqtt-client`)는 토픽만 잇고 서비스를 못 이어서 **우리 다리 노드를 직접 짠다**(JSON만 다루므로 200줄 안팎) |
| **E-30** | **PL 질문 "이 구조가 맞나" — 맞다. 보완 4가지:** ⓐ 서비스 5개(command · check_design · get_design · save_build · stop · resume)는 req/res 토픽으로(E-29 ③) ⓑ 웹 PC(브로커)가 죽으면 화면 정지 버튼이 닿지 않는다 → **로봇 PC의 키보드 정지 · Ctrl+C · 펜던트는 그대로 작동**(정지 입력 4개 중 화면만 영향). 조립 중 웹 생존 신호가 3초 끊기면 task는 **현재 블록까지 놓고 기다린다**(안, 정지 아님 **→ 10/7 PL: `WAIT_HMI`로 정함 — 웹이 다시 붙고 사람이 [계속]을 눌러야 이어 감, IRD 10.3**) ⓒ 상태는 retained, 명령은 QoS 1 ⓓ 브로커는 유선 LAN 안에서만 열고(`listener 1883`, 인터넷 노출 없음), 인증은 10/8 결정(안: 없음 → 필요하면 비밀번호 파일을 `.env`로) | 검증은 문서담당 에이전트(10/6 18시) |
