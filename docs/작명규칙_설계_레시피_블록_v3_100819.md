## 1. 왜 정하나

- 같은 블록을 부르는 이름이 여럿이었다: `LV1_B001`(옛 IRD 예시) · `DXF_INSERT_3E`(레시피 안) · `001_CHAIR_BENCH_B001`(10/7 규칙).
- `DXF_INSERT_3E`는 CAD 내부 번호(DXF 핸들)라서 **CAD를 다시 저장하면 바뀐다.** 사람 · 노드 사이 이름으로 쓸 수 없다.
- `B001`(놓는 순서)은 **이름만 봐서는 구조에서 어디인지 모르고**, 조립 순서를 바꾸면 이름까지 바뀐다. 블록 이름은 구조(무엇이 어디에)에 붙고, 순서는 조립 방법이 따로 정해야 한다.
- 젠가에서는 **부품(다리 · 좌판) 하나가 블록 여러 개**다. 이름도 부품 → 블록 두 단계여야 한다.

- **용어(10/8 E-69):** 레시피 = **구조 파일**(`_recipe.json`), 조립 방법 = placements(`_placements.csv` / 전달 `placements/2.0`). 옛 설명 '레시피 = 조립 방법(`cad_recipe/1.0` = 순서 · 잡기)'은 바꿨다. 핵심은 **CAD 도면 → 레시피 → 로봇 자동 조립**이고, 생성 · 스캔 설계도 블록 JSON(`blocks/2.0`) → 변환기 ①을 거쳐 같은 형식이 된다.

## 5. 레시피 파일 2개 (정함 E-69 — `placements/2.0` JSON 객체 모양 · CSV 20칸은 PR #93으로 정함)

```jsonc
// recipes/001_CHAIR_BENCH_recipe.json — 구조: 무엇을 어디에 (로봇과 무관, 옛 _structure.json 내용 그대로)
{ "schema": "recipe/2.0", "model_id": "001_CHAIR_BENCH",
  "source_cad": {"filename": "001_chair_bench.dxf", "sha256": "342a…"},
  "parts":  [{"part_id": "PART_001", "size_mm": [75, 25, 15]}],
  "blocks": [{"block": "LEG_001_01", "part_id": "PART_001",
              "center_mm": [-25, 0, 7.5], "R": [[0,-1,0],[1,0,0],[0,0,1]],
              "cad": {"handle": "3E"}}] }

// recipes/001_CHAIR_BENCH_placements.csv — 조립 방법 원본(20칸 = 옛 18칸 + recipe_sha256 + schema(모든 줄 placements/2.0), PR #93)
// 전달(JSON)의 조립 방법 = placements/2.0 객체 — 모양은 PR #93으로 정함
{ "schema": "placements/2.0", "model_id": "001_CHAIR_BENCH", "recipe_sha256": "…",
  "steps": [{"block": "LEG_001_01", "block_id": "001_CHAIR_BENCH_LEG_001_01", "sequence": 1, "stage": 1,
             "grasp": "FLAT_SHORT", "grasp_axis": "WIDTH", "supports": []}] }
```

- 두 파일은 블록 이름으로 잇고, **`recipe_sha256`**(구조 객체를 키 정렬 · 공백 없는 JSON(UTF-8)으로 만든 sha256 — 파일 바이트가 아니라 DB · MQTT로 다시 써도 같은 값)으로 '이 조립 방법은 이 구조에 대해 쓴 것'을 확인한다. CSV 칸 · 전달 객체에 같은 값, 안 맞으면 읽기 거부(한세교 정함, 바꾸지 않음).
- AI 설계도 `blocks/2.0`의 블록 칸: `order` · `x` · `y` · `z`(아랫면) · `ori` + **`role`**(역할[_옵션]) · **`part`**(부품 묶음 정수 — 같은 부품 블록끼리 같은 값, 번호 아님) · **`stage`**(정수, 순서 따라 같거나 1씩 증가) · **`grasp`**(`FLAT|EDGE|STAND`_`SHORT|LONG`), 전체 칸 `design_id` · `family`. 예 `{"order":3,"x":-25,"y":0,"z":15,"ori":"y","role":"LEG","part":1,"stage":2,"grasp":"FLAT_SHORT"}` → 변환기 ①이 `LEG_001_02` · 중심 · R · 받침 · 닫힘 축을 채워 위 두 파일을 만든다. 스캔의 `inferred`는 화면 · GPT 힌트 · DB `designs.blocks`에만 남기고 레시피(조립 방법)에는 넣지 않는다.
- 전달 칸 이름(`block` · `block_id` 등)은 PR #93으로 정했다 — IRD · 코드의 `block_id` 칸은 전체 이름(`<모델ID>_…`)을 담는다.
