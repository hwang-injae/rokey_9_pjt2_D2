## 2. 낱말 — 큰 것부터

| 낱말 | 뜻 | 우리 예 |
|---|---|---|
| PC | 컴퓨터 | 운영 PC · 로봇 PC |
| 컨테이너 | PC 안의 Docker 상자. 라이브러리 충돌을 막고 어느 PC에서나 같은 환경으로 돌린다. **성능(연산량)은 바꾸지 않는다** | `vision`(웹캠) · `hmi`(웹 화면) |
| 패키지 | 노드들을 담은 폴더(ROS 2 빌드 단위) | `d2_task`, `d2_motion` |
| 노드 | **실행되는 프로그램 하나.** `ros2 run`으로 켠다. **그림의 카드 하나** | task, pick_place |
| 클래스 | 노드 안의 코드 묶음. 규칙: **노드 하나 = 노드 클래스 하나 = 파일 하나**. ROS 없이 도는 계산 클래스는 다른 파일로 나눠도 된다(S-14) | task 안의 TaskManager(노드 클래스) · TaskPlanner · RunLogger(계산 클래스) |
| 토픽 | **방송.** 보내는 쪽은 받는 쪽을 모른다. 여럿이 받을 수 있다 | `/d2/task/state` |
| 서비스 | **부탁 → 답 한 번.** 받았는지·결과를 바로 안다 | `/d2/hmi/command` |
| 액션 | **오래 걸리는 부탁.** 중간 보고 → 결과, 도중에 취소할 수 있다 | `/d2/motion/pick_place` |

- 서비스·액션 화살표는 **부탁하는 방향으로만** 그렸다. 답은 같은 길로 돌아온다.
- 우리 이름은 모두 `/d2/` 아래에 있다.

## 4. 카드 하나를 읽는 법

카드는 가로로 세 칸이다.

```text
[입력 — 받는 것]  →  [처리 — 하는 일(① ② ③ … 번호 순)]  →  [출력 — 내보내는 것]
```

1. 다른 카드에서 온 화살표는 **입력 상자**에 닿는다.
2. 입력 상자에서 **카드 안 가는 선**을 따라 그 입력을 쓰는 **처리 번호**로 간다. 가는 선의 색 = 들어온 화살표 색이다.
3. 처리에서 가는 선을 따라 **출력 상자**로 간다.
4. 출력 상자에서 나간 화살표를 따라 **다음 카드의 입력 상자**로 간다.

카드 오른쪽 위에는 패키지 · 파트 · "돌리는 곳"(컨테이너 이름 또는 호스트)이 적혀 있다.

## 5. 흐름 따라가기 — 1번부터 11번

**출발점은 그림 왼쪽 위 web_ui 카드의 맨 위 입력 상자 "사람 버튼 6개"다.**

| 번호 | 그림에서 볼 곳 | 따라갈 색 |
|---|---|---|
| 1 출발 | 위 왼쪽 **web_ui** → 위 가운데 **task**. 음성은 web_ui 오른쪽 **voice** | 파랑 |
| 2 관측 자세로 | task 출력 `move_to` → 파랑 띠 왼쪽에서 두 번째 **pick_place** → 맨 아래 회색 **브링업** | 검정 |
| 3 손목 카메라 확인 | task 출력 `check_progress` → 파랑 띠 맨 왼쪽 **wrist_block** | 초록 |
| 4 진행표 | task 카드 안 **"클래스 TaskPlanner"** → 출력 `task/progress` → 파랑 띠 가운데 **scene_manager** · web_ui | 초록 · 보라 |
| 5 블록 옮기기 | task 출력 `pick_place` → **pick_place** → **gripper**(오른쪽에서 두 번째) · scene_manager | 검정 |
| 6 결과 | pick_place 출력 맨 아래 "중간 보고 · 결과" → 위로 올라가 task | 검정 |
| 7~9 정지 · 다시 시작 | 파랑 띠 맨 오른쪽 **safety_stop** ↔ web_ui · task · pick_place | 빨강 |
| 10~11 협동 | 다시 위 **web_ui ↔ task**("내 차례 끝" 버튼) | 파랑 · 보라 |

### 1번: 설계 고르기 · 출발 (파랑)
- **화면:** web_ui 입력 "사람 버튼 6개" → 처리 ① "버튼을 명령으로" → 출력 `/d2/hmi/command (서비스)` → **파랑** → task 입력 첫 번째 → 처리 ① "명령 받기".
  - 순서: **설계 선택**(`select_design`) → **모드**(`set_mode`: 자동 · 협동) → **출발**(`start`).
- **음성:** voice 입력 "마이크" → 처리 ①②③(웨이크워드 → 받아 적기 → 뜻 분류) → 출력 `/d2/hmi/intent (토픽)` → **파랑** → task 입력 두 번째 → 처리 ①.
- **출발 방법은 2가지다(S-16): 화면 출발 버튼, 또는 음성.** 둘 중 아무거나 하나로 출발한다. 작업 관리자는 음성 출발(`start`)을 화면 출발 버튼과 똑같이 받는다. 음성으로 어떻게 출발시킬지(어떤 말, 확인 단계를 둘지)는 HMI 담당이 정한다.
- 출발은 **쉬는 상태 + 시작 점검 통과** 때만 받는다(로봇 알람 없음 · 그리퍼 응답 · 손목 카메라 살아 있음 · 정지 노드 방송 옴).
- 버튼이 서비스인 이유: task가 "안 됨, 이유"를 바로 답할 수 있어야 해서다. 음성은 "들었다"만 알리는 토픽이고, 받아들일지는 task가 정한다.
- task 출력 `/d2/task/state (토픽)` → **보라** → web_ui 입력 → 처리 ② 화면 표시. 상태가 바뀔 때마다 나간다(모드 · 상태 · 차례 · 블록 · 알림 글).

### 2번: 관측 자세로 (검정)
- task 처리 ② → 출력 `/d2/motion/move_to (서비스)` → **검정** → pick_place 입력 두 번째 → 처리 "(move_to) 관측 · 홈 자세로 이동".
- pick_place 출력 `move_group (MoveIt2)` → 회색 브링업 → 팔이 움직인다.
- **`move_group`** 은 MoveIt2의 중심 노드다(우리가 만들지 않음). 이름의 group은 함께 움직일 관절 묶음(M0609 관절 6개)이다. 하는 일은 ① 장면(지도) 들고 있기 ② 부딪히지 않는 길 찾기 ③ 찾은 길을 **ROS 쪽 컨트롤러**(`dsr_moveit_controller`, 브링업 안의 프로그램)에 넘기고, 컨트롤러가 **로봇 제어기**(M0609 제어기 장치)로 보낸다.
- 팔을 움직이라고 하는 노드는 pick_place 하나뿐이다. 그래야 명령이 엇갈리지 않는다.

### 3번: 손목 카메라로 확인 (초록, 서비스)
- task 처리 ③ → 출력 `/d2/vision/check_progress (서비스)` → **초록** → wrist_block 입력 두 번째.
- wrist_block 처리: ① 찍기(장치 D435i → 회색 선으로 영상 · 깊이) → ② 블록마다 있음/없음 → ③ 윗면 높이(top_z).
- 답 "check_progress 답"은 같은 길로 task에 돌아온다. 상태 값은 `present` · `absent` · `occluded`(가림) · `unknown`이다. 높이(top_z)처럼 **재지 못한 값은 0이 아니라 NaN**으로 보낸다. ±2 mm 판정은 1차 뒤다.

### 4번: 진행표 만들기 → 장면 · 화면 (초록 · 보라, 토픽)
- task 안에서 답을 **TaskPlanner**로 넘긴다(카드 안 회색 선 ③ → ⑧, 같은 노드라 함수 호출).
- ⑧ 진행표 갱신 → 출력 `/d2/task/progress (토픽)`. 받는 쪽은 둘이다.
  - **초록** → scene_manager 처리 ①: 놓인 블록(사람이 놓은 것도)을 MoveIt2 장면에 상자로 넣는다 → 출력 `apply_planning_scene` → 브링업. 그래서 다음에 팔이 피한다.
  - **보라** → web_ui 처리 ②: "3/11, B003 사람이 놓음"을 표시한다.
- ⑨ 다음 블록 정하기: 순서에서 안 놓인 첫 블록(받침 있음), 공급 칸 · 자세 · 잡기. 카드 안 회색 선 ⑨ → ④로 5번에 넘긴다.
  - 다음 블록이 없으면 이유: `DONE`(완성) / `BLOCKED_BOTH_SIDES` · `NO_SUPPORT`(사람에게 부탁) / `UNKNOWN_BLOCK`(한 번 더 보고, 또 그러면 사람 호출).

### 5번: 블록 1개 옮기기 (검정, 액션)
- task 처리 ④ → 출력 `/d2/motion/pick_place (액션)` → **검정** → pick_place 입력 첫 번째 → 처리 ①~⑥.
  - ① approach — 공급 칸 위로 → `move_group`
  - ② grasp — 내려가서 닫기 → `/d2/gripper/command` → gripper가 Modbus로 RG2를 닫고, 다 닫히면 "잡힘 · 폭"을 답한다
  - ③ attach — `/d2/motion/scene/attach` → scene_manager가 쥔 블록을 팔에 붙인다(손에 든 블록까지 포함해 피함)
  - ④ lift → move → place — 4번에서 넣은 블록들을 피해서 놓는다
  - ⑤ detach — scene_manager가 떼어 "놓인 블록"으로 남긴다
  - ⑥ retreat — 위로 물러난다
- 액션인 이유: 오래 걸리고, 중간 보고가 필요하고, 멈추면 도중에 취소해야 해서다.

### 6번: 결과 → 다시 확인 (검정)
- pick_place 출력 "중간 보고 · 결과" → **검정** → task 입력 네 번째 → 처리 ④(결과 받기) · ⑤(실패면 실패 대응표: 다시 · 다음 칸 · 사람 호출).
- ⑩ RunLogger → CSV에 한 줄. DB(점선)는 1차 뒤다.
- 성공이면 2번 → 3번으로 돌아가 **방금 놓은 블록이 제자리에 있는지** 확인한다. 11개가 끝나면 완성.

### 7번: 멈추기 (빨강)
- **1차 정지 입력 4개:**
  - 화면 정지 버튼 · 키: web_ui 처리 ③ → 출력 `/d2/safety/stop (서비스)` → **빨강** → safety_stop 입력 첫 번째
  - 로봇 알람: 브링업(두산 드라이버) → safety_stop 입력 두 번째
  - Ctrl+C: 로봇을 움직이는 프로그램(pick_place)이 **스스로 먼저 서기 궤적**을 보낸다(pick_place 처리 마지막 줄)
- **safety_stop 처리:**
  - ① 멈출지 판단 — 판단은 이 노드 한 곳에서만
  - ② 서기 궤적 — `/joint_states`로 지금 관절값을 받아 "지금 자리에 0.3초 안에 서라"를 출력 `FollowJointTrajectory` → 브링업 → 제어기로 **직접** 보낸다. MoveIt2 · pick_place를 거치지 않아서 그쪽이 바쁘거나 멈춰 있어도 선다
  - ③ 2초 안에 안 서면 두산 `move_stop`. 그래도 안 서면 펜던트
  - ④ 출력 `/d2/safety/state` 방송 → **빨강** 세 갈래: pick_place("(멈춤) 목표 취소") · task(처리 ⑦ 멈춤) · web_ui("멈췄어요 · 이유")
- 펜던트 비상정지와 두산 충돌 감지는 이 그림과 상관없이 늘 작동한다.
- **1차에는 웹캠이 로봇을 세우지 않는다.** webcam_human → safety_stop의 빨간 **점선**은 10/8(W066)에 붙인다. 음성 '멈춰'(voice_stop)도 점선이다.

### 8번: 잠금 — 사람이 정리
- 정지 노드는 멈춘 뒤 **잠금**을 건다. 잠긴 동안 task는 아무 목표도 보내지 않는다.
- web_ui 처리 ④: 그리퍼에 블록이 쥐여 있으면 **"블록을 빼 주세요"**. 쥔 블록은 사람이 뺀다. 쥐었는지는 그리퍼 노드가 1초에 1번 + 바뀔 때 내보내는 `/d2/gripper/state`(폭 · 잡힘)로 안다(10/6 S-21 — 그림의 gripper → web_ui · task 선).

### 9번: 다시 시작 (빨강) → 관측부터
- web_ui "다시 시작" 버튼 → 처리 ③ → 출력 `/d2/safety/resume (서비스)` → **빨강** → safety_stop 처리 ⑤ 잠금 풀기 → ④ `safety/state` 방송 → task 처리 ⑦ **"잠금 풀리면 관측부터 자동 이어 감"** → 2번 → 3번 → 4번.
- 관측부터 하는 이유: 멈춘 사이 무엇이 바뀌었는지 모른다(놓다 만 블록 · 사람이 뺀 블록 · 밀린 블록). 사람이 뺀 블록은 진행표에서 "비었음"이 되고 나중에 다시 집는다.
- 잠금은 화면 "다시 시작" 버튼으로만 푼다.

### 10번: 협동 — 사람 차례 (보라)
- 모드 버튼(또는 음성) → `set_mode coop` → task 처리 ①.
- 1차 협동 = **번갈아 하기**(로봇 → 사람 → 로봇 …).
- 사람 차례: task 처리 ⑥ — 로봇은 **관측 자세에서 멈춰 기다린다.** task 출력 `/d2/task/state`(차례 = 사람, 알림 글 "블록을 놓아 주세요") → **보라** → web_ui 표시.
- task 처리 ⑨에서 양쪽이 막혀 그리퍼가 못 들어가는 칸(`BLOCKED_BOTH_SIDES`)이나 받침 없는 칸(`NO_SUPPORT`)이 나오면 알림 글로 사람에게 부탁한다.
- 1차 안전: 사람 차례에는 로봇이 움직이지 않음 + 협동 속도 제한 + 펜던트 · 화면 정지 + 충돌 감지. 웹캠은 방송만 한다.

### 11번: 내 차례 끝 → 로봇 차례 (파랑 → 3번부터)
- 사람이 web_ui **"내 차례 끝"** → 처리 ① → `hmi/command {turn_done}` → **파랑** → task 처리 ①·⑥ → 차례 = 로봇, 화면에 "곧 출발".
- 이미 관측 자세라 바로 **3번(확인)** → **4번 진행표**: 사람이 놓은 블록이 "놓임, 누가 놓음 = 사람"으로 들어간다(로봇이 안 놓았는데 놓여 있으면 사람이 놓은 것).
- scene_manager가 그 블록을 장면에 넣고, 로봇은 피해서 **5번**을 한다. **사람이 놓은 블록은 진행표가 유일한 정보다.**
- 챌린지 ④: 버튼 대신 "손이 3초 안 보이면 자동으로 차례 넘김"(점선).

## 6. 자주 묻는 것

| 질문 | 답 |
|---|---|
| `check_progress`와 `progress`는 뭐가 다른가 | `check_progress` = **서비스**. task가 wrist_block에게 "봐 줘" → 블록마다 있음/없음 · 높이(카메라가 본 **원재료**). `progress` = **토픽**. TaskPlanner가 원재료에 기억(누가 놓음 · 설계 위치)을 합쳐 만든 **현황판(진행표)**, 블록 11개 전부 |
| 장면은 카메라 영상인가 | 아니다. 장면 = MoveIt2가 길을 찾을 때 쓰는 **부딪히면 안 되는 물체들의 3D 지도**(1차: 쌓인 블록 + 쥔 블록 상자). 카메라 → `check_progress` 답 → 진행표 → scene_manager가 **설계 위치에 블록 크기 상자**를 넣는다. 애매한(unknown) 블록도 안전하게 넣는다. 좌표 기준은 로봇 바닥(`base_link`) |
| 손가락 충돌 모델은 뭔가 (scene_manager ③) | MoveIt2가 아는 **그리퍼 손가락의 모양·크기**. 모델이 실제보다 크면 좁은 틈에서 계획이 실패하고, 작으면 실제로 옆 블록을 친다. 고무 패드를 빼서 두께가 바뀌었으니 실측값(robot.yaml `finger.*`)으로 맞춘다(W103). 토픽이 아니라 켤 때 설정 파일을 읽어서 선 대신 입력 상자 'robot.yaml'로 그렸다 |
| 진행표는 누가 고치나 | task 안 TaskPlanner 하나만. 관측할 때마다(블록 하나 놓을 때마다) 다시 쓴다. 나중에 켠 노드도 마지막 진행표를 바로 받는다 |
| 컨테이너에 넣으면 빨라지나 | 아니다. 같은 PC라 연산량은 같다. 컨테이너는 라이브러리 충돌을 막는 상자다(`vision` = MediaPipe numpy 2 ↔ ROS numpy 1.26). 과부하는 노드를 다른 PC로 옮기거나 해상도 · Hz를 줄여 푼다(10/7 부하 측정, 70% 넘으면 비전을 다른 PC로) |
| 정지는 왜 제어기에 직접 보내나 | MoveIt2나 pick_place가 바쁘거나 멈춰 있어도 서야 해서다. 그래서 판단은 safety_stop 한 곳, 서기 궤적은 컨트롤러에 직접 |
| 다시 시작하면 왜 관측부터인가 | 멈춘 사이 바뀐 것을 모르기 때문이다. 진행표는 마지막 관측 기준이라 다시 봐야 맞다 |
| 이 노드는 언제 켜나 | 로봇 PC 먼저(브링업 → safety_stop → 나머지), 운영 PC 나중(컨테이너 2개 → voice · task). task는 켜지면 대기 + 시작 점검을 하고, 다 켜져야 출발을 받는다 |

## 8. IRD와 달랐던 곳 — 10/6 PL 결정

그림 v2는 IRD를 줄이고 정리한 안이었다. 10/6 PL이 아래처럼 정했고, [IRD](02_인터페이스_IRD_v1_100609.md) · [SDD](03_설계_SDD_v1_100609.md)를 이 결정에 맞췄다. 결정 번호는 [결정 기록](decisions/결정기록_시나리오_역할_인터페이스_1004_v1_100609.md) 10/6 절.

| 예전 IRD | 그림 v2 안 | 10/6 PL 결정 |
|---|---|---|
| `/d2/task/next_block` 서비스 · 작업 판단 노드 따로 | **task 노드 하나**(TaskManager + TaskPlanner + RunLogger). 다음 블록은 함수 호출 | ✅ 그림대로 — task 노드 하나, `NextBlock` 없앰 (S-18) |
| `/d2/task/notify` 토픽 | `/d2/task/state`의 **알림 글** 칸 | ✅ 그림대로 — `state`의 `message_id` · `message` (S-19) |
| `/d2/safety/stop_request` 토픽 | `/d2/safety/stop` **서비스** | ✅ 그림대로 — 전용 메시지 `StopRequest`(source · reason → success · message) (S-20) |
| `/d2/motion/halt` 토픽(정지 노드 → 집기 · 놓기) | pick_place가 `/d2/safety/state`를 받아 목표 취소 | ✅ 그림대로 — `halt` 없앰. `safety/state`는 바뀔 때 + QoS TRANSIENT_LOCAL(늦게 켠 노드도 마지막 상태를 받음) (S-26) |
| `/d2/gripper/state` 토픽 | 없음 — `gripper/command` 답에 잡힘 · 폭 | **그림을 바꿈 — 유지**(1초 1번 + 바뀔 때 → task · web_ui). 멈춘 뒤 실제 그리퍼 상태를 아는 유일한 길 (S-21) |
| `/d2/vision/heartbeat` | 없음(1차) | **그림을 바꿈 — 유지, 이름 '카메라 연결 신호', ROS 이름 `/d2/vision/camera_status`.** 1차는 보내기만, 정지 연결은 10/8 W066 (S-22 · S-27) |
| 관측 자세 이동 방법 없음 | `/d2/motion/move_to` **서비스**(관측 · 홈) | ✅ 그림대로 — `MoveTo`(target = observe · home) (S-23) |
| 다시 시작 = `safety/resume` 뒤 `hmi/command resume` | `safety/resume`으로 잠금이 풀리면 task가 **관측부터 자동으로** 이어 감 | ✅ 그림대로 — 버튼 한 번, 누르면 바로 움직임 (S-24) |

- 잡기 이름도 10/6에 바꿨다: `SIDE_25` → `FLAT_SHORT`, `END_75` → `FLAT_LONG` (6가지, S-25 — IRD 2장).
- 멈춘 뒤 배치 다시 알아보기(1차, 10/6 비전 결정): 관측 자세에서 레시피 설계 위치마다 ROI → 깊이 약 10프레임을 모아 윗면 높이 → 예상 층 높이와 비교해 있음·없음·애매함(`present`·`absent`·`unknown`) → 애매하면 같은 자세에서 1번 다시 관측 → 그래도 애매하면 사람 호출. 멈추기 전후 깊이 비교는 보조로만 쓴다(이전 프레임이 늘 남는다는 보장이 없음). 가까이 가서·다른 자세에서 다시 보기는 1차에 넣지 않는다(W058 재보정 뒤 정확도가 모자라면 더함). 높이 허용 오차는 W058 재보정 + W022 녹화로 비전이 정한다.
